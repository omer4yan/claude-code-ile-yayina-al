My learning journey

7 modules 40 lessons Claude Code ile Yayına Al

I finished the seven modules of the course; here I've put together what I learned in each module from my own notes. I'm continuing to learn and put it into practice.

The course follows a path that starts with typing the first commands in a terminal and ends with publishing my own website. Under each module you'll find an example I picked from my notes and the main idea that stuck with me.

My journey Module 01

Install Claude Code

First steps in the terminal

6 lessonsModule 01

I started the course by getting to know the terminal. The first exercises were done in a practice terminal running in the browser; this is where I learned to ask which folder I was in, list its contents, and create a new project folder and move into it.

Lessons

  1. 1
    Terminal, in your browser

    A first project folder in the browser's practice terminal with pwd, ls, mkdir and cd.

  2. 2
    Your first file

    Asking Claude for a hello.txt file, then verifying the result with ls and cat.

  3. 3
    Where did that file go?

    The idea of a working directory; where files are saved, and moving up one folder with cd ...

  4. 4
    When Claude gets it wrong

    Stopping with Esc, undoing with /rewind, stating what you observed and what you expected, and starting over with /clear if needed.

  5. 5
    What Claude is allowed to do

    Reading the approval screen, permission modes and the scope of an "always allow" permission.

  6. 6
    Module 1 summary

    The location, request, check mental model and a quick reference of the basic commands.

What I learned in this module

  • I learned to find out where I am, move between folders and check the contents of files with pwd, ls, mkdir, cd and cat.
  • I learned to ask Claude to create a file with an ordinary sentence, and not to settle for "done" but to open the file and verify its contents myself.
  • I learned to stop with Esc when something goes wrong, go back with /rewind and open a clean conversation with /clear. I also noted that /rewind is not a backup.
  • Instead of clicking through approval screens out of habit, I learned to read which file will be changed and how, and the difference between permission modes.
What stuck with me

Location, request, check: first I know where I am, then I say clearly what I want, and finally I check the result myself.

NextModule 02 — Your first prompt
My journey Module 02

Your first prompt

6 lessonsModule 02

In this module I installed Claude Code on my own computer and, with my first real prompt, created a one-page website called index.html. What I really learned, though, was how a good request is put together.

Lessons

  1. 1
    Anatomy of a prompt

    Installing Claude Code on Windows, a first index.html and the "where, what, why" template.

  2. 2
    The clarity lever

    Naming the file and the property instead of making a vague request; asking for suggestions first when unsure.

  3. 3
    Context windows and /clear

    What context is; the difference between /clear and /compact.

  4. 4
    Slash commands

    /clear, /compact, /rewind, /help, /model, /init and /exit.

  5. 5
    @file and @directory

    Pointing to the right file or folder with @ and using context sparingly.

  6. 6
    Module 2 summary

    Prompts that are specific about the task and sparing with context.

What I learned in this module

  • I learned to build a prompt around "where, what and, when needed, why". Adding the purpose helps Claude make the related decisions in the right direction too.
  • I saw the difference between vague requests like "make it better" and naming the file and the property to change. Clarity doesn't mean length.
  • I learned that context isn't unlimited; to use /clear when switching to an unrelated task and /compact when the same task runs long.
  • I got to know slash commands such as /help, /model and /init, and pointing to the right file with @.
What stuck with me

Look before you leap: if I'm not sure, I first ask for a review and suggestions; then I choose which change to make.

NextModule 03 — Single-file edits
My journey Module 03

Single-file edits

5 lessonsModule 03

In this module I learned to read what a change will do before approving it. Every proposed edit is an offer; accepting, adjusting or rejecting it is my decision.

Lessons

  1. 1
    Reading a diff

    - and + lines; scanning a large diff by file, scope and what is being removed.

  2. 2
    Accepting and adjusting edits

    Accepting a proposal, adjusting it with short feedback or rejecting it.

  3. 3
    Asking for explanations

    Having the file and the proposed change explained before changing anything.

  4. 4
    Small refactors

    Tidying up code without changing how it looks; moving colours into CSS variables.

  5. 5
    Module 3 summary

    Ask → read the diff → accept or adjust → check the page.

What I learned in this module

  • I learned that in a diff, lines starting with - are removed and lines starting with + are added. I noted to scan a large diff in the order "which file, how much change, what is being removed".
  • I learned to choose deliberately between accepting a proposal, adjusting it with short feedback like "a little smaller", or rejecting it.
  • I saw that asking Claude for an explanation before changing a part I didn't understand makes the decision easier. An explanation doesn't replace checking the result.
  • I learned that refactoring means tidying up code while keeping its appearance and behaviour, and to move forward in small steps such as collecting colours into named CSS variables.
What stuck with me

Ask → read the diff → accept or adjust → check the page. The smaller the change, the easier it is to review.

NextModule 04 — Build a multi-page site
My journey Module 04

Build a multi-page site

5 lessonsModule 04

Once a site has more than one page, a change affects other files too. In this module I learned to ask for a plan before editing and to break the work into small, checkable pieces.

Lessons

  1. 1
    Why planning matters

    Asking for a plan with a file list and an order before editing; plan mode.

  2. 2
    Edits across files

    Adding a shared menu consistently to every page and testing the links.

  3. 3
    Breaking tasks into pieces

    Splitting big work into natural steps and stopping to review after each one.

  4. 4
    Reviewing your own diff

    Going through the whole site; checking completeness, consistency, links and real content.

  5. 5
    Module 4 summary

    Plan → change → review the diff → check the pages.

What I learned in this module

  • I learned to ask for a plan instead of an edit first: to have it list which files will be touched in what order, and to read the plan for scope, order and boundaries.
  • I learned that a shared element such as a common menu must be consistent across all pages, and to test the links one by one in the browser.
  • I learned to break big tasks like "build my whole site" into natural steps and to stop and review the result after each step.
  • When the work is done, I learned to go through the site as a first-time visitor would, looking for placeholders, half-finished sections and forgotten links.
What stuck with me

Plan → change → review the diff → check the pages. Before saying "done", you have to actually look at the result.

NextModule 05 — Ship your first project
My journey Module 05

Ship your first project

6 lessonsModule 05

The files on my computer don't open on anyone else's screen. In this module I learned the basic workflow for moving a site from local files to a public web address.

Lessons

  1. 1
    Localhost vs. the live web

    The difference between file://, localhost and a public HTTPS address.

  2. 2
    Git: the five commands you need

    init, add, commit, remote add and push; descriptive commit messages.

  3. 3
    Deploying to Vercel

    Connecting a GitHub repository to a host; checking the file name and path when you get a 404.

  4. 4
    Environment variables and secrets

    Keeping secrets out of the code and the repository; replacing a leaked key.

  5. 5
    Domains, HTTPS and really going live

    Registering a domain, A and CNAME records, HTTPS and the "stranger's tour".

  6. 6
    Module 5 summary

    Commit → push → verify the deployment → check.

What I learned in this module

  • I learned the difference between file://, localhost and a public HTTPS address.
  • I learned to keep a project's history and push it to GitHub with Git's five basic commands. Also that a commit message is a note to my future self.
  • In the course I saw the workflow of connecting a GitHub repository to Vercel and publishing it; I learned to compare the file name and path when a page returns a 404.
  • I learned that secrets such as passwords and API keys must not get into the code or the repository, and that a leaked key is fixed by replacing it, not by deleting it.
  • I learned how a domain, DNS records (A and CNAME) and HTTPS fit together, and to browse the site on another device before publishing.
What stuck with me

Commit → push → verify the deployment → check the live site. These skills are less about memorising commands and more about understanding what each step does.

NextModule 06 — Hooks, MCP and workflow
My journey Module 06

Hooks, MCP and workflow

6 lessonsModule 06

This module was the move from giving one-off requests to organising the way I work. The common goal was to make the right information permanent and to reduce repeated work with the right tool.

Lessons

  1. 1
    CLAUDE.md: teach Claude your project

    Writing down the project, how to run it, preferences and boundaries in a permanent instruction file.

  2. 2
    Slash commands and subagents

    Saving a frequent request as a command; handing a large task to a focused helper.

  3. 3
    Hooks: automate the boring parts

    Automations that run a command on a specific event, and testing them.

  4. 4
    MCP: give Claude new tools

    Connecting to external tools and data sources with the least access needed.

  5. 5
    Beyond the terminal: Agent SDK

    Moving a workflow that has been verified by hand into a program.

  6. 6
    Module 6 summary

    Moving repetition to the right place: a project note, a command, an automation or a connection.

What I learned in this module

  • I learned to write down the project, preferences and boundaries in a permanent instruction file with CLAUDE.md.
  • I got to know saving a frequent request as a custom slash command, and handing large, self-contained tasks to subagents.
  • I learned that hooks run a defined command when a specific event happens, and that this is different from saying "do this every time".
  • I learned that external tools and data sources can be connected to Claude with MCP, and that this should be done with the least access needed.
  • I saw that a workflow can be moved into a program with the Agent SDK, but that it should first be verified by hand.

I've got to know these tools; I'm still trying out and learning how to use them in my own work.

What stuck with me

Move repetition to the right place: if information repeats, put it in a project note; if a request repeats, make it a command; if mechanical work repeats, turn it into a tested automation.

NextModule 07 — Capstone: publish your own site
My journey Module 07

Capstone: publish your own site

6 lessonsModule 07

The goal of the last module was to plan and publish a small site that can actually be used and shared with others. Everything I had learned in the previous modules came together here.

Lessons

  1. 1
    The capstone brief

    Choosing a small site format you'll really use and reading the page plan first.

  2. 2
    Build the pages, deploy on day one

    First the skeleton and a shared menu, then an early deployment.

  3. 3
    Fill it with real content

    Replacing placeholders with real information, adding your own image and keeping the facts intact.

  4. 4
    Add a way to reach you

    Clear contact links; a form service and an end-to-end test if needed.

  5. 5
    Polish, review and publish

    A deliberate decision to publish after checking mobile, links, HTTPS and content.

  6. 6
    Module 7 summary: you shipped

    The plan → describe → review → check → publish → repeat loop.

What I learned in this module

  • I learned to choose a site format I'll actually use, keep the scope small and read the page plan before building.
  • I learned to set up the skeleton of all pages first and verify the publishing workflow early.
  • I learned to replace placeholders with my own information and, while wanting the text to sound natural, to care about keeping the facts exactly as they are.
  • I learned to add a clear way for visitors to reach me, and to check the mobile view, links and content one last time before publishing.
What stuck with me

Plan → describe what you want → review the diff → check the result → publish the finished piece → repeat.
